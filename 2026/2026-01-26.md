## Clawdbot 是什么、能做什么
- **自托管个人 AI 助手**：跑在你自己的电脑/服务器上，通过你常用的聊天软件（含 Telegram）跟你对话、做事。citeturn1view0turn4view0  
- **多通道收消息+回消息**：WhatsApp/Telegram/Slack/Discord… 统一进一个 Gateway 控制面。citeturn1view0  
- **工具能力**：带浏览器、定时任务（cron）、会话/路由、Canvas 等“可执行”工具面板。citeturn1view0  
- 典型用法：清邮箱、发邮件、管日历等（取决于你配置了哪些账号/技能）。citeturn4view0  

## 安装（两种常用方式）
### 方式 A：官方一键安装脚本（最省事）
```bash
curl -fsSL https://clawd.bot/install.sh | bash
```
它会自动处理 Node 22+、并默认走 `npm install -g clawdbot@latest`。citeturn6view2  

### 方式 B：你自己装 Node 后，全局安装
要求 Node ≥ 22，然后：
```bash
npm install -g clawdbot@latest
```
citeturn1view0turn6view0  

## 初始化（建议走向导）
```bash
clawdbot onboard --install-daemon
```
向导会把 Gateway 服务装成常驻后台（launchd/systemd user service）。citeturn1view0turn5view1  

## 跑起来（Gateway）
```bash
clawdbot gateway
# 或前台运行
clawdbot gateway run
```
注意：默认要求你在 `~/.clawdbot/clawdbot.json` 里配好 `gateway.mode=local`，不然会拒绝启动（安全护栏）。citeturn5view0

## 和 Telegram 怎么结合（Bot API）
Clawdbot 的 Telegram 通道是 **Telegram Bot API**，默认 **长轮询**（webhook 可选）。citeturn6view1  

### 1）在 Telegram 里创建机器人（BotFather）
- 打开 Telegram，找 `@BotFather`
- 执行 `/newbot`，按提示设置名字和用户名（以 `bot` 结尾）
- 拿到 **bot token** 保存好 citeturn6view1  
可选：  
- `/setjoingroups` 控制能否被拉群  
- `/setprivacy` 控制群里是否“只看指令/提及”还是“看全部消息” citeturn6view1  

### 2）把 token 配进 Clawdbot（推荐写配置；也可用环境变量）
- 环境变量：`TELEGRAM_BOT_TOKEN=...`  
- 或配置：`channels.telegram.botToken: "..."`（配置优先级更高）citeturn6view1  

最小配置长这样（概念示例）：
```json
{
  "channels": {
    "telegram": {
      "enabled": true,
      "botToken": "123:abc",
      "dmPolicy": "pairing"
    }
  }
}
```
citeturn6view1  

### 3）启动 Gateway，然后去 Telegram 私聊你的 bot
- 第一次私聊时，默认是 **pairing**：陌生人只会拿到一个配对码，bot 不会处理内容。citeturn6view0turn6view1  
- 你在命令行批准配对：
```bash
clawdbot pairing approve <channel> <code>
```
批准后会把你加入本地 allowlist。citeturn6view0  

### 4）进群玩法（避免群里“被刷屏带跑”）
建议先保持“需要提及才响应”（例如 `@你的bot` 才触发），再逐步放开。Telegram 文档里也给了 groups 的提及门控例子。citeturn6view1

## 重要安全提醒（别跳过）
Clawdbot 直接连真实聊天面，**把所有外部私信当不可信输入**；默认 pairing 是为了防止别人随便给你喂指令。citeturn6view0  
如果你把 `dmPolicy` 改成 open，相当于把“遥控器”丢到公共场合，除非你非常确定自己的 allowlist/沙箱策略。citeturn6view0

## Prediction Market Factory (1USD Accelerator)

### What it is
A **$1-entry micro prediction market**. Each topic is a simple YES/NO market, where **price equals probability**. Users put real value behind their beliefs, and the market compresses scattered opinions into a clear **price curve**, creating a signal that’s easy to cite, screenshot, and spread.

- **Fundraising:** It converts “community hype” into measurable data (price, volume, activity/heat, participants). Investors love this: quantifiable, reviewable, and iteratively improvable.  
- **Recognition:** This is not a poll. It’s **belief with cost**. Being wrong costs money, being right can earn money, so the signal is more credible to judges and ecosystem partners.

### What you can do (how to participate)
- **Trade with a slider:** Pick YES/NO plus a confidence level (1–99). The system quotes an estimated cost, then you confirm the trade.  
- **Move the probability:** Your trade updates the market probability. Higher confidence moves it more, and costs more.  
- **Watch and share:** Each market has a real-time curve and heat/activity indicators, built for virality and growth.

### What edge you get
- **Monetize information advantage:** If you know earlier or judge better, you can enter before the price moves.  
- **Use the curve as a radar:** Price/volume/heat changes are trend signals, useful for spotting narratives, projects, memes, or sector momentum.  
- **Low-cost experimentation:** At $1 scale, “betting your opinion” becomes a controllable experiment, great for mass onboarding.

### Key technical stance (so it’s a “real thing”)
- **Final ledger is on-chain:** Positions (YES/NO shares), funds, and state updates are auditable on-chain.  
- **Off-chain is quote + UX only:** Off-chain handles quoting/signing/caching/indexing for UI, but does not own the final ledger.

可以。Docker 这样跑起来以后，**域名最终能访问到网站**，常见有两种接法：

## 方案 1：最快能用（但不优雅）
把域名 A 记录指向服务器 IP，然后直接访问：

- `http://你的域名:3000`  （前端）
- `http://你的域名:3001`  （后端）

前提：防火墙放行 3000/3001 端口。

缺点：要带端口号，不好看；HTTPS 也麻烦；很多反代/CDN不爱代理这种端口。

---

## 方案 2：推荐的“正式上线”方式（域名不带端口 + HTTPS）
做一个 **Nginx 反向代理**，让域名走 80/443，然后转发到 Docker 的 3000/3001。

### 1) DNS
域名添加一条 A 记录：
- `@ -> 服务器IP`
- `www -> 服务器IP`（可选）

### 2) 服务器装 Nginx
```bash
apt update -y
apt install -y nginx
```

### 3) Nginx 配置（前端走 /，后端走 /api）
新建：`/etc/nginx/sites-available/liqpass.conf`
```nginx
server {
  listen 80;
  server_name yourdomain.com www.yourdomain.com;

  # 前端（Vite dev / 或你未来的静态站）
  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;

    # 兼容 Vite/WebSocket 热更新（dev 时用）
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
  }

  # 后端 API
  location /api/ {
    proxy_pass http://127.0.0.1:3001/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
  }
}
```

启用并重载：
```bash
ln -s /etc/nginx/sites-available/liqpass.conf /etc/nginx/sites-enabled/liqpass.conf
nginx -t && systemctl reload nginx
```

### 4) HTTPS（Let’s Encrypt）
```bash
apt install -y certbot python3-certbot-nginx
certbot --nginx -d yourdomain.com -d www.yourdomain.com
```

### 5) 前端请求怎么写（关键点）
把前端 API 基地址写成**相对路径**：`/api`  
这样就不怕 CORS，也不用写死 IP/端口。

---

### 结论
- 你现在这种 Docker 跑 dev 服务，**完全可以先用域名接入**（方案2 也能接）。
- 真正上线时，把前端改成 build 后由 Nginx 静态托管会更稳，但不影响你先把域名跑通。

- 第二条如果返回 **401/405/200**：✅ 路由存在，前端只需改 baseURL/代理
- 如果还是 **404**：后端路由前缀不一致（可能真实是 `/api/accelerator/projects`）

## 5) 前端改法（等你确认后端端口后立刻改）
**不要再写 `http://localhost:3000`**。推荐用 Vite proxy：

`vite.config.ts`：

```ts
server: {
  proxy: {
    "/accelerator": { target: "http://localhost:<后端端口>", changeOrigin: true },
  },
}
```

前端请求保持相对路径：

```ts
post("/accelerator/projects", data)
```
